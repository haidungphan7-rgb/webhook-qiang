## 1. 必做功能 1：Webhook 收件箱

| 目标要求 | 我的实现 | 为什么这样设计（取舍） | 怎么验证 |
|---|---|---|---|
| 名称 | `inbox.name`；`inbox.go` 建箱处 TrimSpace + 空校验 + 长度 ≤120 | 唯一必填字段，用两个纯函数搞定，**没引 react-hook-form/zod**（全项目只此一处表单） | `curl -XPOST :8080/api/v1/inboxes -d '{"name":"  "}'` → 422 `validation_error: name is required` |
| 唯一标识 | `inbox.id uuid PRIMARY KEY DEFAULT gen_random_uuid()` | **坚持 UUIDv4 不换 ULID/UUIDv7**：每箱硬顶 500 条，B-tree 页分裂代价低于噪声；换 ID 要动 storage/crypto(AAD)/DTO/全部测试 | 列表返回 `"id":"…"`；换 ID 访问别人的 → 404 |
| 难猜测且唯一的 Token | `storage/token.go`：`crypto/rand` 32 字节 → 31 字符无歧义字母表 `abcdefghijkmnpqrstuvwxyz23456789`（去掉 0/O/1/l/I）→ 51 字符；`inbox.token UNIQUE` | 借鉴参考项目 `whinspector/slug.ts`。token 要**被口述、被贴进聊天、被抄进第三方后台**，去掉易混字符消灭一整类工单；256 bit 熵 → 不可枚举。不用 UUID（太长且有 `-`），不用裸 base32（含易混字符） | 列表里 `token` 字段长度 51 |
| 是否启用 | `inbox.enabled boolean default true`；`PATCH /v1/inboxes/{id}` 传 `{"enabled":false}` | 用 `*bool` 指针 + `InboxPatch` 语义，让「停用」与「没提到」可区分（否则 PATCH 无法表达 false） | 停用后 `curl -XPOST :8080/hooks/<token>` → 403 `inbox_disabled` |
| 创建时间 | `inbox.created_at timestamptz default now()` | 全库 timestamptz，UI 按本地时区渲染 | 列表 `created_at` |
| 创建 / 列表 / 启停 | `POST`、`GET`（带 q/enabled/limit/offset + `total`）、`PATCH`。**额外**：`DELETE`、`POST /v1/inboxes/{id}/token/rotate` | 轮换 token 是刚需（token 泄露即失效），成本 10 分钟 | `curl -XPOST …/token/rotate` → 新 token，旧地址立刻 404 |
| 接收入口 `POST /hooks/{token}` | `webhook/middleware.go:extractToken`，命中即 `handleCapture` | **做成中间件而不是路由**：请求命中即返回，永不进路由表，也永不可能被 SPA 兜底成 200 HTML | `curl -XPOST :8080/hooks/badtoken` → 404（不是 200 HTML） |
| 接收入口免登录 | `server.go` 只把 `/api/` 挂在 `httpapi.New` 下；`/hooks/` 走中间件，**不在 auth 链上** | 照抄 `whinspector/auth.ts` 的边界："Capture routes must NOT use this"。第三方永远无凭据投递 | 配 `--auth-token` 后 `/hooks/<token>` 仍 200，`/api/v1/inboxes` 变 401 |

### 2.1 七类信息

### 2.2 四条规则

| 规则 | 实现 | 为什么不是另一种做法 | 怎么验证 |
|---|---|---|---|
| Token 不存在 / 停用 → 拒绝 | 不存在 **404**，停用 **403** | 404 而不是 403：403 会泄漏"这个 token 存在"。**停用用 403 是刻意的**——此时调用方需要知道"地址对但被关了" | `middleware_test.go: TestCapture_UnknownTokenIs404` / `TestCapture_DisabledInboxIs403` |
| 请求体 ≤ 1MB，超过 413 **且不保存** | Content-Length 预检 + `http.MaxBytesReader(w, r.Body, limit+1)` | ① **`max+1` 是全部诀窍**：`io.LimitedReader` 对"正好满"和"超出"都返回 EOF，只有多读那 1 字节才能区分。② 用 `MaxBytesReader` 而不是"读完再判"：后者会先把 1GB 读进内存再拒绝 | `TestCapture_ExactlyAtLimitIsStored`（正好 1MiB→200）、`TestCapture_OneByteOverLimitIsRejected`（+1→413 且库里 0 条）、`TestCapture_HugeBodyIsNotBuffered`（10MiB 不缓冲） |
| 成功返回事件 ID | `{"id":"...","ok":true}`，另加响应头 `X-Wh-Event-Id` | 头 + body 都给：脚本党读头，人读 body | `curl -i -XPOST …/hooks/<token>` |
| 原始体保留；JSON 美化只做展示 | `event.body bytea` 不改写；前端 `prettyPrint()` 只影响渲染；传前端用 `body_base64` | **不把美化后的 JSON 回写**：回写会改变重放发出的字节，也让接收方的 HMAC 校验失败。base64 而非 JSON string：`encoding/json` 解码会把非法 UTF-8 换成 U+FFFD | `TestCapture_BodyIsPreservedByteForByte`（含 NUL / 非法 UTF-8 / CRLF 逐字节断言） |

### 4.2 2xx 语义、目标限制、可验证、重定向

| 目标要求 | 实现 | 为什么不是另一种做法 | 怎么验证 |
|---|---|---|---|
| 2xx = 成功；其它 = 已收到响应但业务失败 | `service.go` | 明确区分 `success` / `http_error`，不笼统叫"失败" | `TestRun_HTTPErrorIsRecorded`：500 仍存预览 `boom` |
| HTTP 200 的语义 | `/replay` 返回 `{"ok":…,"attempts":[…],"last":{…}}`，**HTTP 200 只表示"尝试已执行并已记录"** | 否则前端无法区分"重放失败"与"接口调用失败" | 重放 `/fail` → HTTP 200 但 `ok=false` |
| 目标地址限制策略 | `blockedIP()`：loopback、**0.0.0.0/8**、RFC1918、CGNAT、链路本地 169.254/16（含云元数据）、192.0.0/24、benchmark、组播/广播、IPv6 ULA、链路本地、**6to4 2002::/16**、**NAT64 64:ff9b::/96**、IPv4-mapped；`Transport.Proxy` 恒 nil | 选"阻断保留地址"而不是"白名单域名"：调试工具的靶子本来就是多变的。**0.0.0.0/8 和 6to4/NAT64 是 reviewer 揪出来的**——`ip.IsUnspecified()` 只挡 `0.0.0.0` 一个地址，而 Linux 把整个 /8 当本机 | 49 条用例逐条断言 |
| 可验证 | **被拒绝的尝试也落一条 `outcome=blocked` 记录** | 最漂亮的一处：需求说"限制必须可验证"，那就让拒绝本身出现在历史里，而不是只在日志里 | `curl -XPOST …/replay -d '{"target_url":"http://169.254.169.254/"}'` → **403** 且在 `GET …/replays` 里能看到这条 blocked |

### 4.10 UI 上的七种状态：六种落库结果 + 两个"当次才有"的状态

`shared/components/outcome-badge.tsx` 里的 `Outcome` 是**七种**，比落库的五种多两个。原因是：**"服务端记录了什么"和"用户此刻需要知道什么"不是同一件事。**

| UI 状态 | 徽标 | 落库 outcome | 会出现在历史里 | 用户该做什么 |
|---|---|---|---|---|
| `success` | 成功 | `success` | ✅ | 对比多次尝试的状态码与耗时 |
| `http_error` | 非 2xx | `http_error` | ✅ | 查路径/方法/鉴权头（Authorization、Cookie 不转发） |
| `timeout` | 超时 | `timeout` | ✅ | 确认可达，或调大 `replay-timeout` |
| `network_error` | 网络错误 | `network_error` | ✅ | 查 DNS/端口/TLS；内网与保留地址会被拒绝 |
| `blocked` | 被拦截 | `blocked` | ✅ | 改用 http(s) 公网地址（请求从未发出） |
| `rate_limited` | 已限流 | **不落库** | ❌ | 等倒计时（限流器在 handler 之前就拒绝了） |
| `invalid_target` | 地址不合法 | **落库是 `blocked`** | ❌（显示为「被拦截」） | 改写法（必须 http(s) 开头、不能带用户名密码、必须带主机名） |

两个"多出来"的状态，差别在于它们与落库值的关系：

- **`rate_limited`：没有任何落库对应物。** 限流中间件 `limited()` 在 `createReplay` 之前就返回 429，一条 attempt 都不会生成。它是界面上一定会遇到的状态（带倒计时的错误卡）。
- **`invalid_target`：有落库对应物，但语义不同。** `ValidateTarget` 返回 `ErrInvalidURL`（地址写错）时，`Service.Run` 仍然走 `blockedAttempt()` 落一条 `outcome=blocked`。**数据库里区分不了"地址写错"和"地址被策略拒绝"**。若照结果卡说「请改用 http(s) 公网地址」，对忘了写 `http://` 的人就是错误建议。所以 UI 用 `invalid_target` **替换掉结果卡**，改口说"改写法就行，与内网无关"。

**为什么 `invalid_target` 不进 `OUTCOME_LIST`：** `OUTCOME_LIST` 是"帮助页那张结果表"的数据源，语义是"**历史里能查到的状态**"。把它列进去，帮助页会多一行「地址不合法」——而用户翻遍历史也看不到这一行（它只会显示成「被拦截」）。**列一个查不到的状态，比不列更糟。**

配套的「结果卡 vs 错误卡」互斥规则（都在 `screens/event/screen.tsx`）：

- 失败后**先回读历史**；历史里有记录 → 只显示结果卡（服务端已落库的那条是唯一真源）
- 只有 `invalid_target` 例外：只显示错误卡、隐藏结果卡（结果卡会给出错误建议）
- 其余"连 attempt 都没生成"的失败（429、5xx、网络不通）→ 显示错误卡

### 4.3 SSRF 三层（最值得讲的地方）

| 层 | 位置 | 抓什么 |
|---|---|---|
| ① 提交时校验 | `ValidateTarget` | scheme、userinfo、DNS 解析**任一**结果是保留地址就拒（防 round-robin 混入私网） |
| ② 拨号时复检 | `checkDialAddress`，挂在 `transport.DialContext` 包装里 | 防 DNS rebinding；"每连接都跑"天然覆盖重定向每一跳 |
| ③ 重定向复检 | `CheckRedirect` | 公网 URL 302 到内网 |

## 5.2 验证路径

`scripts/smoke.ps1` 是"四步走通"的冒烟自检；`scripts/acceptance/` 下是断言脚本（可用 `make accept` 一次跑完），它们覆盖同一个链路但给出的是通过/失败，靠人要读的是日志而不是"证明"。

前置（另一个终端，注意 `--replay-timeout 3s` 是刻意的：D7 演示超时只等 3 秒，而不是 10 秒的尴尬沉默）：

```powershell
go run ./cmd/webhook-tester start --port 8080 `
    --replay-allow-host 127.0.0.1 --replay-allow-private --replay-timeout 3s
```

| 步 | 动作 | 证明什么 | 预期看到 | 翻车了怎么说 |
|---|---|---|---|---|
| **D1** | 创建收件箱 | 收件箱模型 + token 不可猜测 | 201；token **51 位**、不含 `0/1/l/o` | 422 → 名字是空的（唯一必填字段） |
| **D2** | 发一条带 `authorization` 的请求 | 捕获口免鉴权 + 返回事件 ID + 实时推送 | 200 `{"id":"…","ok":true}`；头里有 `X-Wh-Event-Id`；**浏览器不刷新就出现** | 没出现 → 看 WS 连接徽标；确认浏览器停在哪个收件箱 |
| **D3** | 看敏感头 | 凭据类请求头入库前就被处理 | `Authorization = ***redacted***` | 若是明文 → 服务没配 `--encrypt-key` 时是**不可逆掩码**，这正是"宁可丢也不明文落库" |
| **D4** | 发 1048576 与 1048577 字节 | 限制在**读取阶段**生效，超限不落库 | 正好 1 MiB → 200；+1 → **413 且事件数不增加** | 两条都 200 → 限制没生效；两条都 413 → 少了 `max+1` 判据 |
| **D5** | 重放到 `127.0.0.1:9099/ok` | 重放成功 + 敏感头不转发 | `success` / `200`；**接收端打印的 headers 里没有 `authorization`** | 403 → 服务没带两个 allow 开关，**正好把 SSRF 防护提前讲** |
| **D6** | 重放到 `169.254.169.254` | SSRF 防护 + **拒绝本身留痕** | 403 `target_blocked`；`GET …/replays` 能看到一条 `blocked` | 要点：**一条请求都没发出，但留下了记录**——限制可验证 |
| **D7** | 重放到 `/slow` | 超时独立成一类；2xx 才算成功 | `timeout`，`duration_ms` ≈ 3000 | 这里最适合说"结果分六类，响应体读不全也不算成功" |
| **D8** | `GET …/export?format=curl` | 闭环到"我在自己机器上复现" | 可直接粘贴的 curl，**不含明文敏感头** | 相对路径 → 没配 `--public-url-root`，命令顶部有注释提示（**宁可提示也不假装能用**） |

## 6.5 第五个页面：应用内使用说明（`/help`）

需求只要求 4 个页面，这是第五个——不是凑数，是因为"重放的规则"这类信息放哪里都不对：放 README，用户操作时看不到；放 Modal，会挡住他正在操作的东西。

**为什么是独立页而不是 Modal**（三条，都是实测出来的）：

1. **要边看边发 curl。** 核心动作是"照着那段 curl 去终端发一条"。Modal 一开就盖住页面。
2. **要能 Ctrl+F 全页搜索。** 使用说明注定被搜索（"限流多少"、"超时多少"），Modal 里既不好滚也不好搜。
3. **要能分享、能深链。** 独立页有 URL，可以把 `/help#replay` 发给同事；Modal 没有地址。

**这一页最重要的设计：所有数值运行时实读 `/api/v1/settings`。**

一份写死的文档**从落笔那一刻就开始漂移**：默认超时 10s，哪天运维用 `--replay-timeout 30s` 起服务，页面还写 10 秒——界面开始骗人，而且毫无痕迹。

| 页面上的值 | 来源 | 顺带修掉的问题 |
|---|---|---|
| 超时 N 秒 | `replay_timeout_ms` | 改启动参数页面跟着变 |
| 请求体上限 | `max_request_body_size` → `formatBytes()` **并给原始字节数** | 只写"1 MiB"会留下 1000/1024 歧义 |
| 响应预览 | `replay_max_preview` | 同上 |
| 限流 | `replay_rate_limit`（0 显示"不限"） | 关掉时不会显示"0 次/分钟"这种鬼话 |
| 敏感头清单 | `sensitive_headers`（服务端返回） | **清单不可能与二进制矛盾** |
| 白名单主机 | `replay_allow_hosts`（非空才显示） | 没配就不显示 |

页脚写着「以上数值来自当前服务实例的 `/api/v1/settings` · 读取于 HH:mm:ss」——**连"什么时候读的"都告诉你**。`api.go` 的注释原话是："a guide that contradicts the binary is worse than no guide at all"。

# 第二部分：一步一步是怎么实现的

## 1. 底座选型：为什么是 E，为什么是它

**选 E 的理由**（按"二开+裁切+打磨总工作量"重排后 E 反超到第一，5.5–6.5h）：
- 五题里**唯一"底座功能 ⊆ 需求功能"**的：裁切几乎为零，二开全是新增独立模块（PG 驱动/重放服务/attempts 表），不碰已有模型；
- 只要 4 个页面，单位打磨成本最低；
- 底座已有请求体上限、WS、内嵌 React；MIT 许可证。

被淘汰的对照（答辩素材）：
- **A（Flipt）看起来最省其实最贵**：模型三层而需求只要一层；裁切清单含 gRPC/5 种存储/4 种认证/OTel/SDK；GPL-3.0；老 React+Redux。
- **C 基本无现成**，只能自研。
- **D（seatsurfing）** GPL-3.0 且模型是工位/会议室，改语义成本高。

底座内部还对比了 `whinspector`（Node+PG+SSE）——**抄了它的三点**：无歧义 token 字母表、`ACCESS_TOKEN + timingSafeEqual + 接收入口不鉴权`的边界、模型形态。也**发现它两处不如目标要求**（写进 README 当加分）：`replay.ts` 只剥 hop-by-hop 头，**不剥 Authorization/Cookie/X-API-Key**；**完全没有 SSRF 防护**（只判 protocol，能打 169.254.169.254）。

## 2. 骨架搭建与「切掉 oapi-codegen」

**必须切的原因（不是偏好，是硬约束）**：上游用 `oapi-codegen` 同时生成 Go 服务端骨架和 TS 客户端，但**生成文件不入库**。后果：clone 之后不跑 `go generate`（还得先装 Node）**根本编译不过**。生产交付要求"克隆即构建"，所以：
- 删 `internal/http/openapi*`、`internal/http/handlers/`、`api/openapi.yml`；
- 手写 `internal/httpapi` + 手写 `web/src/api/v1.ts`；
- 写进 `AGENTS.md` 第 1 条"不可协商规则"。

**代价**：契约有两处（Go DTO ↔ TS 类型），靠人工同步。**为什么值得**：换来"clone → go build → 跑起来"，这是交付给别人看的第一道门槛。

顺带裁切：删 redis/fs 存储驱动、ngrok 隧道、healthcheck 子命令、version 外网查询；删 `--auto-create-sessions`（与"难猜测 token"直接冲突）、改 `--max-requests`（会静默丢事件）。

## 3. 数据模型与迁移

三张表：`inbox` / `event` / `replay_attempt`，外键全 `ON DELETE CASCADE`。

**`body_text` 是怎么来的 —— 最值得讲的一次翻车**：
1. 最初关键字搜索写的是 `convert_from(e.body,'UTF8') ILIKE '%q%'`；
2. PostgreSQL 对非法 UTF-8 抛 **SQLSTATE 22021**，且 `text` 根本不能含 NUL；
3. 后果：一个 gzip/protobuf/含 0x00 的 webhook 进去之后，该收件箱**所有带 `?q=` 的列表永久 500**；
4. 修复：加 `body_text` 列，`CreateEvent` 时用 `storage.SearchableText()`（规则 = `utf8.Valid && !bytes.Contains(0)`，封顶 **64KiB** 且按 rune 边界截断——1MiB 正文会让 trigram 索引膨胀到比数据还大）写入；查询改 `body_text ILIKE`；
5. **不把 `SearchableText` 放在某个驱动里**：抽到 `storage` 包，PG 与 mem **必须共用**。因为复审发现 mem 比 PG 宽松 → **二进制 bug 的回归测试在 mem 上根本复现不出来（假绿）**；
6. 历史行由迁移 **0003** 回填。踩坑：`position(E'\000'::bytea …)` 无效（text 字面量不能含 NUL），必须写 `'\x00'::bytea`；且 `convert_from` 要放在**独立的 BEGIN/EXCEPTION** 里赋值，不能放在 UPDATE 的 WHERE 中（否则一行坏数据会中止整个回填）。

**为什么不用 golang-migrate/goose**：3 个表、4 个 SQL，自研 60 行（embed.FS + 事务 + `schema_migrations`），二进制自包含、启动即迁移、无版本漂移。迁移 0004 还修了一个"死索引"：`event_inbox_ct_idx` 建在 `(inbox_id, content_type)` 上，但查询谓词是 `lower(split_part(content_type,';',1))`，普通索引**永远用不上** → 改成表达式索引。

## 4. 接收入口改造

顺序：解析 token → 查库 → 停用/不存在 → OPTIONS → ContentLength 预检 → `MaxBytesReader` → 签名 → 落库 → 发布 → 响应。

- **`/hooks/<非法 token>` 不能落 SPA**：早期实现在 `extractToken` 里校验字母表，非法就交给下游，结果返回 200 HTML（对扫描器和用户都是噪音）。改成"只要前缀匹配就进捕获流程"，由捕获 handler 统一 404。
- **1MB 的 `max+1` 判据**：`io.LimitedReader` 对"正好满"与"超出"都返回 EOF，只有多读 1 字节才能区分。
- **敏感头两条路径**：有密钥 → AES-GCM 加密；无密钥 → `***redacted***`。`protect()` 里加密失败**返回掩码而不是明文**（fail closed）。
- **来源 IP 不能由请求头决定**：初版由请求头决定是否信 XFF，客户端自己就能伪造 → 改成 `Deps.TrustProxy`，由配置项 `--trust-proxy-headers` 传入。
- **发布用 appCtx 不用 request ctx**：响应一发 request ctx 就取消，订阅者会丢事件。

## 5. 重放服务：三层 SSRF，以及为什么被迫从 `Control` 改成 `DialContext`

**全项目最硬的一段。**

初版设计：第 2 层用 `net.Dialer.Control` 做每连接复检，理由是"Control 拿到的是真实 IP，能防 DNS rebinding，且每连接都跑，天然覆盖重定向每跳"。

**翻车**：`http.Transport` 传给 `Dialer.Control` / `DialContext` 的 address 是 **`host:port` 形式的主机名**，不是 IP——解析发生在 `net.Dialer` 内部。于是"域名 = 绕过解析器 = 拒绝"的实现，**会让所有公网域名重放全部失败**。更糟的是 reviewer 给的测试用例也基于同一个误解，说明这个坑非常隐蔽。

**正解**：把复检包在 `transport.DialContext` 里，`checkDialAddress(ctx, addr)` 自己 `SplitHostPort` → 字面 IP 直接判、域名则走 `lookupIP`（带 5s 超时 + 测试 seam）解析后逐条判。测试侧的 `dialRouter` 也要**按域名做 key**。

为什么值得讲：
1. 它证明了"每连接复检"这个设计意图是对的，只是挂错了钩子；
2. 它证明**让 reviewer 与实现分离是有效的**——两人一起踩同一个坑，但第二轮复审把它挖出来了；
3. 修完之后测试反而更强了：现在能真正覆盖"DNS 名解析到私网/公私混合/空答案/解析失败"四种情况，且**不依赖外网 DNS**。

配套决策：
- **AllowHosts 只能收窄不能放宽**：要重放到保留地址，必须**同时**传 `--replay-allow-host` 和 `--replay-allow-private`；`config.Validate()` 启动时校验"allow host 是字面保留地址但没开 AllowPrivate"→ 直接报错。
- **`Proxy` 恒 nil**：不读代理环境变量，否则 `HTTP_PROXY` 会成为绕过路径。
- **被拒绝也落库**：`blockedAttempt()` —— "限制可验证"落到数据上。

| 测试踩坑 | 测试 token 必须只用无歧义字母表（"testtoken" 含 `o` 会被判非法 → 全 404）；Go 会**自动重算** Content-Length（应断言"不等于捕获值"而非"为空"） |

## 8. 多租户与归属校验

`--auth-keys alice:<kA>,bob:<kB>` → `auth()`（`subtle.ConstantTimeCompare`）解析出租户 → 写进 request context → `ownerKey()` 从 context 取 → `ListInboxes` 带 `owner_key` 过滤。

**关键补充**：光有列表过滤不够，**每个按 ID 的接口都要校验归属**（`ownedInbox`/`ownedEvent`）——否则拿到/猜到 UUID 就能读别人的数据（IDOR）。别人家的资源返回 **404 不是 403**："它存在"本身也是信息。事件、重放、导出、WS 订阅全部走同一套校验。

token 只从 `Authorization: Bearer` 或 HttpOnly Cookie 读，**不支持 `?access_token=`**（URL 会进访问日志、浏览器历史、Referer）。

## 10. 从"能用"到"敢演示"：产品打磨轮

> 前面九节做完时：README 齐了、测试绿了、需求逐条对上了。然后 pm 拿了一把很朴素的尺子来量——**一个从没见过这个仓库的人，照着 README 走，3 分钟能不能成功重放一次？**
>
> 答案是不能，而且失败方式是最坏的一种：不是"说清楚为什么失败"，而是"把你引向错误的方向"。
>
> 这一节讲的都是同一类问题：**功能是对的，但人用不起来**。它们的共同点是——跑测试发现不了，只有真的坐下来操作一遍才会遇到。

### 10.1 pm：默认配置下第一次重放必然失败，而且提示是误导的

**现象。** 按 README 四步：建箱 → 发一条 → 打开详情 → 目标填 `http://127.0.0.1:9099/ok`（README 自己让你起的接收端）→ 点「重放」→ 显示 **「网络错误：无法与目标建立连接」**。演示者于是去查接收端、端口、防火墙——**全查错方向**。真实原因只是：服务端默认拒绝内网地址，请求根本没发出去。

**根因（两处叠加）：**
1. 服务端对 `ErrBlockedTarget` 返回 **403**，而前端 `classifyReject()` 只认 429 和 400，其余兜底成 `network_error`；
2. 更糟：403 响应体里**其实带着 `attempts` 数组**，但 `request()` 在 `!res.ok` 时直接 throw，**body 被丢掉**。

**修法（三层，缺一不可）：**
1. **打字时就提示**：`shared/utils/target-check.ts`，命中内网就黄字说明，并复用服务端的 `replay_allow_hosts`/`replay_allow_private` 判断是否真的放行；
2. **规则常驻可见**：重放面板底部常驻一行（转发什么、不转发什么、目标必须 http(s) 非内网、超时 N 秒 + 链到 `/help#replay`）。**不塞进「高级选项」**——塞进去等于"只有失败过的人才知道"；
3. **失败后先回读历史**：catch 里先 `await loadReplays()`；只要服务端已落 attempt（`blocked` 一定会落），就**只显示结果卡、不显示错误卡**。

**为什么不是另一种做法：**
- **为什么不让前端把内网地址拦死？** 浏览器**解析不了主机名**——`foo.internal` 是否指向内网只有服务端知道；白名单也是服务端配置。拦死会误伤"本实例已显式放行"的场景。所以 `checkTarget` 分三级：`error`（协议不对/带用户名密码/缺主机名）才禁用按钮，`warn`（内网）只警告，**它是提示，不是执行**——执行永远在服务端。
- **为什么不把 403 也加进映射表？** 那会出现"结果卡说被拦截 + 错误卡也说被拦截"两份判决。**让服务端已落库的那条当唯一真源**——这与"删 Dexie、服务端为唯一数据源"是同一条原则的两次应用。
- **为什么不改 `request()` 返回 4xx 的 body？** 那只是"从错误响应里捞数据"；回读历史才是唯一真源，还顺带解决"刷新后错误卡没了但历史还在"。

**验证**：`reports a blocked target through the result card only` —— 桩 403 + 历史里一条 `blocked`，断言出现「目标被安全策略拒绝」、**不出现**「没有发起重放」、事件本体仍在、服务端英文不外泄。

### 10.2 designer：结果卡色条整条 CSS 被丢弃

`outcomeColor()` 把 `META` 的色值 token 拼进 CSS 变量，得到 `var(--mantine-color-green.8)`。而 Mantine 的变量用**连字符**（`green-8`）——点号让整条 `var()` 无效，浏览器**丢弃整条 `border-left`**。

**为什么"不实测发现不了"**：不报错、不进控制台、类型检查也过得去——CSS 变量无效是静默失败。

**为什么不是改 `META` 写成连字符**：同一个 token 有两个消费者、两种语法：Mantine 的 `color` prop 只认点号，CSS `var()` 只认连字符。所以转换放在"唯一出口函数"里。顺带把色值映射收敛到一处——此前事件页还有一条手写三元链，两处必然漂移。

### 10.3 designer：复制按钮在 http + 局域网 IP 下静默失效

`navigator.clipboard` 只在**安全上下文**（https 或 localhost）存在；局域网 IP + http 下是 `undefined`，而 Mantine 的 `useClipboard` **没有 `execCommand` 回退，还把失败吞掉**——调用方永远以为成功了。

自写 `copyText`：① `clipboard.writeText` ② 回退离屏 textarea + `execCommand('copy')` ③ **返回 boolean**，由调用方降级（弹手动复制窗 / 黄色通知）。

**关键不是"它没有回退"，而是它不告诉你失败了**——没有返回值就无法触发降级 UI，用户只会以为"按钮坏了"。**一个会失败的操作必须把失败交给调用方。**

### 10.4 tester：保留策略从未执行过，以及单测为什么假绿

清理任务用 `ListInboxes(ctx, InboxFilter{...})`，`OwnerKey` 是零值空串；而真实行的 `owner_key` 是 **`'default'`** → 空串匹配 0 行 → 一条都没删。**它不是错误，是"合法地查到了空结果"**，所以既不报错也不告警。

**为什么单测假绿**：夹具里的 `storage.Inbox{...}` **没设置 OwnerKey**（零值 `""`），过滤条件也是 `""` → 全部命中 → 通过。**夹具复制了实现里的同一个错误假设，于是测试把 bug 保护了起来。**

修法三处：① `InboxFilter.AllOwners`（默认 false = 按 owner 过滤，注释写明"忘设就 fail closed"）；② 清理任务显式传 `AllOwners: true` 并注释原因；③ **夹具改成生产数据的形状**（显式 `OwnerKey: "default"`）+ 回归 `TestRunOnce_SweepsEveryTenant`（同时断言"bob 看不到 alice"，避免为了修 bug 把隔离也拆了）。

**为什么不用 `OwnerKey: "*"` 这种哨兵值**：某天真的出现一个叫 `*` 的租户就击穿了；布尔开关没有歧义，且"默认过滤"方向是对的。

### 10.5 组件测试逼出的三个真 bug

这一轮的组件测试**不是为覆盖率，是唯一能发现这三个问题的手段**：

**(a) 被拦截显示成「网络错误」** —— 见 10.1。纯函数测不到，**它错在两个组件之间的协作**（错误卡 vs 结果卡）。

**(b) reveal 开关点了没变化** —— 加载 effect **只依赖 eventId**（当初为"切 Tab 不重载整页"故意这么写），`reveal` 变化不触发任何请求。
> **为什么不直接把 `reveal` 加进依赖数组？** 那个 effect 里还有三件"只在换事件时该做"的事：清空未提交编辑、拉历史、读最近目标。加进去会导致**正在编辑的请求体被打回原样**。拆分而不是加依赖，让"换事件"和"换视图参数"各管一段。

**(c) dayjs 插件只注册在入口，组件一单独渲染就崩** —— `relativeTime` 与 `zh-cn` 只在 `main.tsx` 注册，**配置属于启动序列，不属于依赖**。新建 `shared/dayjs.ts` 配置后再导出，所有组件从它导入。顺带修了"3 minutes ago"混进中文界面的问题。

### 10.6 一个"不造状态"的小修补：`HeaderDTO.revealed`

打开 reveal 后某些敏感头仍显示 `***redacted***`，用户分不清是**"没权限看"**还是**"原值根本没存下来"**。

`capture.Reveal()` 解不开时原样返回掩码（这是对的），但客户端无法分辨。于是 `HeaderDTO` 增加 `revealed`：**只有真的解密成功才为 true**（`revealed = value != h.Value`）。

**为什么不是"前端判断值是否等于掩码就推断不可恢复"？** 那是**本地推断**：掩码是展示格式不是事实；换个掩码写法、或某个头的值恰好就叫 `***redacted***`，推断就错了。**权威来源在服务端，就让它多返回一个字段；补不出就明确"不可恢复"，而不是猜。**

## C. 收尾轮的六个缺陷：三个"功能对但结果错"，三个"配置/交付层"

前三个的共同点是：**它们都不报错**。没有异常、没有红字、日志干净，只有结果是错的。

### C1. 保留策略在 PostgreSQL 上从未执行过

- **现象**：`--retention-max-events 500` 配了，事件数一路涨到几千。
- **根因**：`retention.RunOnce` 用空 `OwnerKey` 列收件箱，而 PG 侧无条件拼 `i.owner_key = $1`，真实行的 `owner_key` 是 `'default'` → 恒 0 行 → 每轮遍历 0 个收件箱。**它不是错误，是"合法地查到了空结果"**，所以日志里一个字都没有。
- **为什么单测假绿**：单测跑在 `mem` 驱动上，夹具的 `OwnerKey` 也是零值 `""`，而 mem 的过滤同样是相等比较 → `"" == ""` 全命中 → 绿。**夹具复制了实现里的同一个错误假设，于是测试把 bug 保护了起来。**
- **修法**：`InboxFilter.AllOwners`（默认 false = 按 owner 过滤，忘设即 fail closed）；清理任务显式传 `true`；夹具改成 `OwnerKey: "default"`，新增 `TestRunOnce_SweepsEveryTenant`。
- **验证**：真机塞 600 条，一轮后剩 500，日志出现 `retention: pruned events`。

### C2. 修 C1 时引入的二次 bug：`AllOwners` 时 SQL 以 `WHERE ` 结尾（42601）

- **根因**：`AllOwners` 时 `where` 切片可能为空，而代码固定拼 `" WHERE " + strings.Join(...)`。
- **修法**：把关键字并进条件——`cond := ""; if len(where) > 0 { cond = " WHERE " + ... }`。
- **为什么不是加 `1=1`**：那能跑，但它把"这里确实没有任何过滤条件"藏了起来。
- **最大的教训**：**内存驱动测不出 SQL 语法错误**。这是本项目第三次"驱动/夹具分叉"。凡拼 SQL 的改动都要在真库上跑一遍。

### C3. 敏感头 reveal 在 UI 上完全失效

- **根因**：前端 `buildQuery` 把 boolean 序列化成 `"true"`，后端只认 `=="1"`。**两端都没错，合起来错。**
- **修法**：后端新增 `truthy()`，接受 `1 / true / yes / on`。
- **为什么不只改一边**：只改前端，curl/脚本党就坏了；只改后端接受 `true`，哪天又出现 `yes`。**解析布尔值的宽容度属于服务端**。

### C4. `readPreview` 读响应失败仍记 success

- **修法**：改为返回 error，保留已读部分但标记 `preview_truncated` → **响应体读不全不算成功**。
- **为什么不是"2xx 就算成功"**：目标要求 2xx=成功，但"成功"的含义是"这次重放可信"。**宁可标成失败，也不要给用户一个不可信的成功。**
- **实测**：目标返回 `200` 但只发了 7 字节就断连 → `status_code=200`、`outcome=network_error`、`error="cannot read response body: unexpected EOF"`、`preview="partial"`、`ok=false`。

### C5. `UpdateInbox` 读—改—写导致并发覆盖

- **修法**：改成**单条部分 UPDATE**，只为 patch 里出现的列拼 `SET`。
- **为什么不是加乐观锁**：PATCH 的字段都是"最后写入者胜"语义，加版本号要引入冲突处理与重试 UI，收益不抵复杂度。**但"不动没提到的列"必须做**，否则改个名字等于重写签名密钥。

### C6. urfave/cli 的 `StringSliceFlag` 会按逗号再拆一次

- **现象**：`start-secure.ps1 -Tenants alice,bob` → 启动报 `invalid auth key "alice"`。
- **根因**：`$Tenants` 是**一个**字符串 `"alice,bob"` → 生成 `"alice,bob:<key>"` → `StringSliceFlag` 又按逗号拆成 `["alice", "bob:<key>"]` → 第一项没冒号。**一次拆分发生在我以为不会再拆的地方。**
- **修法**：脚本侧先按逗号展开，再**每个租户单独传一次 `--auth-keys`**。
- **为什么不在后端兜**：`<tenant>:<key>` 是后端契约，逗号是多值分隔符，这个语义属于 CLI 框架。

### C7. fresh clone 的 `web/dist` 只是占位页 → `go run` 后是空白页

- **修法**：占位页改成**会说话的中文提示**（「前端尚未构建」+ 两条命令 + 「后端不受影响」），并新增 `web.Stubbed()` → 启动时 `log.Warn`。
- **为什么不只在 README 写一句**：**人遇到空白页的那一刻，他不在读 README**——要在故障发生的那一刻解释。

## D. 交付形态与部署

**交付产物是一个二进制**：前端已 `go:embed`。实测把 `webhook-zq.exe` 单独复制到空目录（没有 `web/`、没有 `node_modules`）也能服务 `GET /` 与 `assets/*.js`。

| 平台 | 体积 |
|---|---|
| Windows x64 | ≈ 15.7 MB |
| Linux x64 | ≈ 15.3 MB |
| macOS ARM64 | ≈ 14.8 MB |

**唯一外部依赖是 PostgreSQL**（`pg_trgm` + `pgcrypto`）。完整内容见 `docs/部署指南.md`：systemd unit（密钥走 `Environment` 避免出现在 `ps`）、Nginx 反代（**`/hooks/` 限流必须由反代做**）、`migrate --check`、升级即替换二进制、回滚要留 `pg_dump`。

**观测只有一个端点要记住**：`GET /api/v1/settings` —— 排障第一步永远是问"这台实例现在到底是怎么配的"。

## E. 为什么没有管理后台

**先给结论**：需求只要求 4 个页面，我做了 5 个。**管理后台不在需求范围内，而且我刻意不做**——不是没想到，是想过之后的判断。

**第一层：管理员真正需要的两个问题，已经有答案了。**

| 管理员想问的 | 现在由什么回答 |
|---|---|
| 「这台服务现在怎么配的？」 | `GET /api/v1/settings` + 顶栏「服务器设置」弹窗 |
| 「为什么这次重放是这个结果？」 | 七种 outcome + 每条的「下一步建议」+ `/help` 规则表 |
| 「服务活着吗？」 | `GET /healthz`（含数据库连通性） |
| 「schema 到位了吗？」 | `webhook-zq migrate --check`（退出码即答案） |
| 「数据会不会无限涨？」 | 收件箱上的保留策略——**它本身就是"自运维"** |

**第二层：「服务器设置」弹窗是给使用者看的，不是给管理员看的。** 它只读、没有任何写操作，回答的是「我现在为什么会这样」，不是「我要把它改成那样」。**给使用者看的配置是"解释"；给管理员改的配置是"控制"。前者我需要，后者我不要。**

**第三层（最硬的一条）**：`--replay-allow-private` 是唯一的 SSRF 闸。一旦做"能在页面上改配置"的后台，这道闸就从**部署时决策**降级成**运行期状态**——一个误点的同事、一个被借走的会话、一台被接管的浏览器，都能把它打开。

> **能在页面上点一下就打开 `--replay-allow-private` 的后台，是给攻击者准备的后台。**

**第四层：真要运维化，优先级比管理后台高的还有三件**（都写在 README §7 与部署指南 §8）：pub/sub 换 Redis 或 PG `LISTEN/NOTIFY`、迁移加 advisory lock、`/hooks/{token}` 入口限流。

**以及一条工程上的诚实**：做任何"能改配置"的后台，前提是先有认证与授权体系。需求不要求登录系统——**在最小可用的 API Key 映射之上再叠一个后台，是给一个还没有门的小屋装指纹锁。**

**30 秒答辩版**：
> 「目标要求 4 个页面，我做了 5 个。管理员真正要的两件事我都有：这台实例现在怎么配的，看 `/api/v1/settings` 和『服务器设置』弹窗（只读）；这次为什么是这个结果，看七类 outcome 和帮助页。至于『在页面上改配置』——`--replay-allow-private` 是这套 SSRF 防护里唯一的闸，把它变成页面上可点的开关，等于把部署时决策降级成运行期状态。**能在页面上点一下就打开它的后台，是给攻击者准备的后台。**」

## F. 如果还有一天会做什么
